# 番組の取り込み — 準正常系・異常系の設計（Issue #101）

> 凡例: **【事実】** 決定済み・コードで確認済み / **【確認済み】** 出典あり / **【仮説】** 未検証 / **【提案】** 未決。ユーザー判断待ち
>
> 対象: `src/services/podcast/PodcastImportService.ts`、`src/app/import.tsx`、`feed_episodes`、話数の採番（REQUIREMENTS.md §2.1.1）。
> 配信基盤（Issue #107）との接続点も含める。

## 1. なぜこの文書が要るか

最初の実装（`claude/rss-import-feature-bknvuu`）は正常系を通すことに寄っていた。
「取り込む」は番組情報・配信済みの回・話数の台帳・アートワークを**まとめて書き換える**操作で、
しかも後で #107 の配信基盤から**配信する元**になる。準正常系・異常系を決めずに進めると、次が起きる。

- 別の番組の回が自分の番組に混ざり、話数の台帳が壊れる（§4 B-1。**今のコードで起きる**）
- 他人の番組を取り込んで、そのまま配信基盤から配信できてしまう（§4 A-2。#107 の実装時に起きる）
- 手で直した番組情報が、読み込み直しで黙って元に戻る（§4 C-5。**今のコードで起きる**）

## 2. 前提【事実】

- MVP は 1 Show 固定（FR-SHOW-1）。取り込みは「今の番組の中身を入れ替える」操作であって、番組を増やす操作ではない。
- 取り込みは端末の中だけで完結する。外に出るのは検索語と RSS の取得だけ（NFR-5）。
- RSS は公開情報。取り込めたことは所有者である証明にならない（FR-SHOW-11）。
- 配信済みの番号は再利用しない（§2.1.1）。台帳は `episodes` と `feed_episodes`。

## 3. 原則【提案】

| # | 原則 | 理由 |
|---|---|---|
| P1 | **取り込みは制限しない。配信の入口で所有権を確かめる。** 取り込みは Podcast アプリで番組を購読するのと同じ「公開情報の写し」で、端末の外に害は出ない。害が出るのは、他人の番組を自分の名前で配信するとき | 取り込みの段階で所有権を確かめようとしても、サーバーが無いので確かめる手段が無い。確かめられるのは #107 の配信基盤 |
| P2 | **書く前に「同じ番組か」を判定する。違う番組なら「差し替え」として扱い、混ぜない** | 配信済みの回と話数の台帳は番組ごとのもの。混ざると元に戻せない |
| P3 | **ユーザーが手で直した値を黙って上書きしない** | 読み込み直しは何度も行う操作（配信状況の更新）。毎回番組情報が戻るなら使えない |
| P4 | **失敗したら何も書かない**（DB もファイルも） | 途中で落ちたときに、半端な状態を残さない（NFR-1 と同じ考え方） |
| P5 | **外から来た値は、使う場所で安全かを確かめる**（URL のスキーム、HTML、長さ） | RSS は誰でも書ける（NFR-10） |

## 5. 同一番組の判定規則【提案】

取り込もうとしている番組（新）と、今の番組（旧）を、上から順に比べる。**最初に決まったもの**を採る。

| 順 | 比べるもの | 一致 | 不一致 |
|---|---|---|---|
| 1 | 旧に何も取り込んでいない（`feed_imported_at` が空） | 初回 → 上書き（確認なし） | — |
| 2 | `podcast:guid`（両方にあるとき） | 同じ番組 | 別の番組 |
| 3 | Apple の番組 ID（両方にあるとき） | 同じ番組 | 別の番組 |
| 4 | RSS の URL（旧の `feed_url` と、新の取得 URL・自己申告の URL・`itunes:new-feed-url` のどれか） | 同じ番組 | 次へ |
| 5 | 回の `guid` の重なり（旧の `feed_episodes` のうち、新の RSS に含まれる割合） | 半分以上が重なれば同じ番組【仮説: しきい値】 | 別の番組 |

- 「別の番組」→ 差し替えの確認（B-1）。確認なしには書かない。
- 「同じ番組」→ 読み込み直し（C-5 の差分表示）。
- 4 で決まらず 5 で「重なりが少ないが 0 ではない」ときは、同じ番組として扱い、C-3 の重複警告を出す。

## 8. 所有権の確認（Spotify for Creators を参考に）【提案】

### 8.1 Spotify for Creators の流れ【確認済み】

1. 「既存の番組を探す」→「ほかのサービス（Somewhere else）」を選び、RSS の URL を入れる。
2. Spotify が RSS の `<itunes:email>`（`itunes:owner` の中）の宛先へ、8 桁の確認コードをメールで送る。送り先は Spotify のアカウントのメールではなく、**RSS に載っているメール**。
3. コードを入力すると、その番組を自分のアカウントで管理できる。

- 出典: [Claiming your podcast on Spotify for Creators](https://support.spotify.com/us/creators/article/claiming-your-podcast-on-spotify-for-creators/)（環境の制限で本文は開けず、検索結果の要約で確認）、[RSS.com: Claim your submitted show](https://help.rss.com/en/support/solutions/articles/44002440660-how-do-i-claim-my-rss-com-feed-on-spotify-for-creators-)、[Buzzsprout: Claim Your Spotify Listing](https://www.buzzsprout.com/help/221-claim-your-spotify-listing)
- 迷惑メール対策で、**RSS にメールを載せない配信サービスが増えている**。確認のときだけ一時的に載せる機能がある（RSS.com は 12 時間、Podbean は 48 時間で自動的に消える）【確認済み】([RSS.com](https://help.rss.com/en/support/solutions/articles/44002405274-how-to-enable-the-email-address-in-the-rss-feed)、[Podbean](https://blog.podbean.com/podbean-removes-emails-from-podcasters-rss-feeds-to-protect-podcaster-privacy-and-reduce-spam/)、[Transistor](https://transistor.fm/changelog/hide-email/))
- メールの代わりに、RSS に確認用の文字列を置く方式もある（`<podcast:txt purpose="verify">`）【確認済み】([podcast:txt](https://podcasting2.org/docs/podcast-namespace/tags/txt))

### 8.2 PodsNow にそのまま持ち込めない点【事実】

**確認コードは、アプリの外（サーバー）で作って照合しないと意味がない。**
アプリの中でコードを作ると、アプリ自身がコードを知っているので、改造すれば確認を飛ばせる。
メールの送信にも送信用の秘密情報が要り、アプリには埋め込めない（#107 §17 と同じ理由）。
したがって、確認は配信基盤（#107、Cloudflare Workers）の機能になる。

### 8.3 段階

| 段階 | 取り込み | 確認 | 配信 |
|---|---|---|---|
| 今（配信基盤なし。開発者 1 人） | できる。番組は「未確認」 | できない | できない（配信基盤が無い） |
| 配信基盤ができたあと | 取り込みの流れの中で確認する（プレビュー → **確認** → 取り込む）。確認を後回しにして「未確認」のまま取り込むこともできる | メールのコード、または RSS の確認用文字列 | **確認済みの番組だけ**配信できる。未確認なら、配信しようとしたときに確認へ誘導する |
| 一般公開 | 同上 | 同上。確認は「アカウント」と番組を結ぶ | 同上 |

取り込み自体を確認必須にしない理由: 確認は通信とメールの受信が要り、失敗しうる（§8.4）。
録音・編集は確認と無関係なので、確認が通らないことで取り込みまで止めない。止めるのは、害が出る配信だけ（P1）。

### 8.4 確認の流れ（配信基盤ができたあと）

```
プレビュー
  └─ 「この番組の所有者か確認します」
       ├─ メールで確認（RSS にメールがあるとき）
       │    宛先は伏せて見せる（ta***@gmail.com）→ コードを送る → 8 桁を入力 → 確認済み
       ├─ RSS に文字列を置いて確認（メールが無い・届かないとき）
       │    PodsNow が文字列を発行 → 配信サービスの設定で <podcast:txt purpose="verify"> に入れてもらう
       │    → 「確認する」で配信基盤が RSS を取得して照合 → 確認済み
       └─ あとで確認する → 未確認のまま取り込む
```

### 8.5 確認の準正常系・異常系

| ID | 状況 | 提案 |
|---|---|---|
| V-1 | RSS にメールが無い（配信サービスが隠している） | 「配信サービスの設定で、メールを一時的に RSS に載せてください」と案内し、主な配信サービスの手順へのリンクを出す。RSS の確認用文字列へ切り替えられるようにする |
| V-2 | RSS のメールが古い・届かない・迷惑メールに入る | 「迷惑メールフォルダを確認」を出す。再送は間隔を空ける（60 秒）【仮説】。届かなければ V-1 と同じく文字列方式へ |
| V-3 | RSS のメールが配信サービスの共通アドレス（本人に届かない） | 同上。文字列方式を勧める |
| V-4 | コードの入力間違い | 5 回で打ち切り、コードを無効にする【仮説】。やり直しは新しいコードで |
| V-5 | コードの期限切れ | 期限は 15 分【仮説】。期限切れなら再送 |
| V-6 | **他人の番組でコード送信を繰り返し、所有者にメールを送りつける**（嫌がらせ） | 番組ごと・端末ごとに送信回数を制限する（例: 1 番組 1 日 5 通）【仮説】。メール本文に「心当たりが無ければ無視してください。番組は変更されません」と書く |
| V-7 | 確認のあとで RSS のメールが変わった | 確認済みは取り消さない。配信基盤への移転時（#107）に改めて確認する |
| V-8 | 共同で運営している番組（複数人が確認したい） | MVP は 1 人。一般公開のときに、確認済みの人が招待する形を考える（#107 FR-PUB-8） |
| V-9 | 確認済みの番組を、別の番組に差し替えた（B-1） | 確認は番組ごと。差し替えたら新しい番組は未確認に戻る |
| V-10 | 確認用文字列を RSS に入れたが、配信サービスのキャッシュで反映が遅い | 「反映まで数分かかることがあります」と出し、何度でも「確認する」を押せるようにする |
| V-11 | `podcast:locked` が yes | 確認とは別に、配信基盤へ移るときに locked を外す手順を案内する（A-3） |

### 8.6 データ【提案】

- 端末: `shows.ownership_verified_at`（NULL = 未確認）と、確認に使った方式。確認の結果は配信基盤が正本で、端末はその写し。
- 配信基盤: 確認コード（ハッシュで保存）・期限・試行回数・送信回数。メールアドレスそのものは保存しない（RSS から都度読む）。
