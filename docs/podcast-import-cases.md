# 番組の取り込み — 準正常系・異常系の設計（Issue #101）

> 凡例: **【事実】** 決定済み・コードで確認済み / **【確認済み】** 出典あり / **【仮説】** 未検証 / **【提案】** 未決。ユーザー判断待ち
>
> 対象: `src/services/podcast/PodcastImportService.ts`、`src/app/import.tsx`、`feed_episodes`、話数の採番（REQUIREMENTS.md §2.1.1）。
> 配信基盤（Issue #107）との接続点も含める。

## 1. なぜこの文書が要るか

最初の実装（`claude/rss-import-feature-bknvuu`）は正常系を通すことに寄っていた。
「取り込む」は番組情報・配信済みの回・話数の台帳・アートワークを**まとめて書き換える**操作で、
しかも後で #107 の配信基盤から**配信する元**になる。準正常系・異常系を決めずに進めると、次が起きる。

- 別の番組の回が自分の番組に混ざり、話数の台帳が壊れる（§4 B-1。**今のコードで起きる**）
- 他人の番組を取り込んで、そのまま配信基盤から配信できてしまう（§4 A-2。#107 の実装時に起きる）
- 手で直した番組情報が、読み込み直しで黙って元に戻る（§4 C-5。**今のコードで起きる**）

## 2. 前提【事実】

- MVP は 1 Show 固定（FR-SHOW-1）。取り込みは「今の番組の中身を入れ替える」操作であって、番組を増やす操作ではない。
- 取り込みは端末の中だけで完結する。外に出るのは検索語と RSS の取得だけ（NFR-5）。
- RSS は公開情報。取り込めたことは所有者である証明にならない（FR-SHOW-11）。
- 配信済みの番号は再利用しない（§2.1.1）。台帳は `episodes` と `feed_episodes`。

## 3. 原則【提案】

| # | 原則 | 理由 |
|---|---|---|
| P1 | **取り込みは制限しない。配信の入口で所有権を確かめる。** 取り込みは Podcast アプリで番組を購読するのと同じ「公開情報の写し」で、端末の外に害は出ない。害が出るのは、他人の番組を自分の名前で配信するとき | 取り込みの段階で所有権を確かめようとしても、サーバーが無いので確かめる手段が無い。確かめられるのは #107 の配信基盤 |
| P2 | **書く前に「同じ番組か」を判定する。違う番組なら「差し替え」として扱い、混ぜない** | 配信済みの回と話数の台帳は番組ごとのもの。混ざると元に戻せない |
| P3 | **ユーザーが手で直した値を黙って上書きしない** | 読み込み直しは何度も行う操作（配信状況の更新）。毎回番組情報が戻るなら使えない |
| P4 | **失敗したら何も書かない**（DB もファイルも） | 途中で落ちたときに、半端な状態を残さない（NFR-1 と同じ考え方） |
| P5 | **外から来た値は、使う場所で安全かを確かめる**（URL のスキーム、HTML、長さ） | RSS は誰でも書ける（NFR-10） |

## 4. ケース

「現在」はこのブランチのコードを読んで確かめた挙動【事実】。「提案」は未決【提案】。
優先度: **高** = データが壊れる・他人に害が出る、**中** = 利用者が混乱する・直すのに手間がかかる、**低** = まれ・害が小さい。

### B. 別の番組・別の経路での取り込み（同一性）

| ID | 状況 | 現在 | 提案 | 優先度 |
|---|---|---|---|---|
| B-1 | 番組 A を取り込んだあと、**別の番組 B** を取り込む | **混ざる。** 番組情報は B で上書き、`feed_episodes` は A の回と B の回が並ぶ、Apple の番組 ID は B で上書き、カテゴリーは B で置換。**話数は A の最大値の続きのまま**（例: A が 120 回、B が 10 回なら、次は #121） | §5 の規則で「別の番組」と判定したら、取り込む前に「番組を差し替える」確認を出す。差し替えでは **A の配信済みの回・外部 ID・カテゴリー・支援リンク・アートワークを消してから** B を入れる。**手元で作ったエピソード（録音）は消さない**。確認文で「配信済みの回 120 本の記録が消え、話数は B の続きになる」と数字で伝える | **高** |
| B-2 | 同じ番組の RSS の URL が変わった（配信サービスの移転。`itunes:new-feed-url` や 301 で移っている） | 別の URL として取り込み、`feed_url` を新しい方に書き換える。回は `guid` が同じなら重ならない | §5 の規則で「同じ番組」と判定し、差し替えの確認を出さない。`feed_url` の変化はプレビューに「RSS の URL が変わりました（旧 → 新）」と出す | 中 |
| B-3 | 同じ番組を、検索経由と URL 直接入力の両方で取り込む | 同じ番組として扱える（`guid` で突き合わせ）。URL 直接入力では Apple の番組 ID を書き換えないので、前の値が残る | 同じ番組ならそれでよい。ただし B-1 の差し替えでは、前の番組の ID が残って食い違うので、差し替え時に消す | 低 |
| B-4 | 「新しく始める」で手元にエピソードを作ったあと（#1〜#3）、配信中の番組（120 回）を取り込む | 取り込める。次は #121。手元の #1〜#3 はそのまま残り、配信済みの #1〜#3 と話数が重なる | プレビューで「手元のエピソード 3 本はそのまま残る。配信済みの回と同じ話数のものがある」と伝える。手元の回を配信済みの回に結びつける（`feed_episodes.episode_id`）のは、話数・題名が一致する候補を出してユーザーが選ぶ形にする（自動では結ばない） | 中 |
| B-5 | PodsNow の配信基盤（#107）へ移ったあとで、**旧配信元の RSS** を読み込み直す | 旧 RSS の内容で上書きする（旧 RSS が 301 で新 RSS を指していれば、新 RSS を読む） | 自分の配信基盤が正本になった番組は、外部 RSS から読み込み直さない。配信状況は配信基盤から取る（FR-PUB-5）。`feed_url` が自分の配信基盤の URL なら、取り込み画面に「読み込み直す」を出さない | 中（#107） |

### C. 同じ番組の読み込み直し

| ID | 状況 | 現在 | 提案 | 優先度 |
|---|---|---|---|---|
| C-1 | RSS に最新 N 件しか載っていない | 載っていない回も残す【事実】 | そのまま | — |
| C-2 | 配信者が回を**本当に取り下げた** | C-1 と区別できず、残る | 各回に「最後に RSS で見た時刻」を持ち、読み込み直しで見えなくなった回は「RSS に無い」と表示する。消しはしない（話数の台帳から外さない。取り下げた番号を再利用すると、リスナーのアプリで混乱する） | 低 |
| C-3 | 配信サービスの移転で、回の `guid` が**振り直された**（本来は規格違反） | 同じ回が別の行として 2 本ずつになる | 読み込み直しで「`guid` が 1 つも重ならない」なら同一番組でも警告する。`enclosure` の URL、または題名と配信日時の一致で重複を検出し、プレビューに「同じ回が重複しそうです」と出す | 中 |
| C-4 | 配信者が話数を直した（#12 → #13） | 上書きする【事実】 | そのまま。手元で既に使った番号と重なる場合は B-4 と同じ扱い | 低 |
| C-5 | 手で直した番組名・概要が、読み込み直しで**上書きされる** | **上書きされる**（RSS に値があれば必ず） | 初回（または差し替え）は上書き。**読み込み直しでは番組情報を上書きせず、RSS 側と違う項目をプレビューに並べて、項目ごとに「RSS の値にする」を選べる**ようにする。回（`feed_episodes`）は常に更新 | **中** |
| C-6 | `guid` が無く、音声の URL で代わりにしていた回の音声 URL が変わる | 別の回として 2 本になる | C-3 と同じ重複検出の対象にする | 低 |

## 5. 同一番組の判定規則【提案】

取り込もうとしている番組（新）と、今の番組（旧）を、上から順に比べる。**最初に決まったもの**を採る。

| 順 | 比べるもの | 一致 | 不一致 |
|---|---|---|---|
| 1 | 旧に何も取り込んでいない（`feed_imported_at` が空） | 初回 → 上書き（確認なし） | — |
| 2 | `podcast:guid`（両方にあるとき） | 同じ番組 | 別の番組 |
| 3 | Apple の番組 ID（両方にあるとき） | 同じ番組 | 別の番組 |
| 4 | RSS の URL（旧の `feed_url` と、新の取得 URL・自己申告の URL・`itunes:new-feed-url` のどれか） | 同じ番組 | 次へ |
| 5 | 回の `guid` の重なり（旧の `feed_episodes` のうち、新の RSS に含まれる割合） | 半分以上が重なれば同じ番組【仮説: しきい値】 | 別の番組 |

- 「別の番組」→ 差し替えの確認（B-1）。確認なしには書かない。
- 「同じ番組」→ 読み込み直し（C-5 の差分表示）。
- 4 で決まらず 5 で「重なりが少ないが 0 ではない」ときは、同じ番組として扱い、C-3 の重複警告を出す。

## 6. 決めてほしいこと

| # | 論点 | 私の推奨 | 他の選択肢 |
|---|---|---|---|
| Q1 | 所有権をどこで確かめるか（A-2） | 取り込みでは確かめない。#107 で配信する前に、RSS の `podcast:txt` で確かめる | 取り込み時にも「自分の番組です」のチェックを求める（強制力は無いが誤操作は減る） |

## 7. 実装への影響（Q1〜Q4 を推奨どおりに決めた場合）

- **データ**: `feed_episodes` に `last_seen_at`（C-2）。取り込み前の状態の退避先（Q4）。`shows` の変更は無し。
- **サービス**: `preview` の結果に「判定（初回 / 同じ番組 / 別の番組）」「番組情報の差分」「重複の疑い」「手元の回と話数が重なる数」を足す。`commit` は判定に応じて「上書き / 選んだ項目だけ更新 / 差し替え」を行う。URL の保存前チェック（E-8）。アートワークの一時ファイル化（E-4）。
- **画面**: 差し替えの確認（数字つき）、読み込み直しの差分と項目選択、直近の回の表示（A-1）、取り込み中の戻る操作の停止（E-5）。
- **テスト**: 本文の ID ごとにテストを書く（テスト名に ID を入れる）。

高の 3 件（B-1 / D-1 / A-2 の #107 側）と、中のうち今のコードで起きる C-5 / E-8 は、#101 を閉じる前に直す。
